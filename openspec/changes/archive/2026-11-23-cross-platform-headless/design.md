# Design

## Context

The Tauri entry point composes `SettingsStore`, `EventBus`, `ConnectionErrors`, the three engines behind `EngineSwitch` and `Runtime`. The core already has a data-directory override, a memory secret store, and blocking shutdown. Vosk and Whisper directly used Windows `libloading` APIs, Sherpa duplicated platform selection, the asset catalogs name only Windows archives, and asset tools and engine discovery assume Windows. The desktop's log filters live in the desktop crate.

Linux support in this design is not tested: nothing of it has been compiled or run on Linux. The user checks it later on Linux; until then every Linux decision below is marked (not tested).

## Goals / Non-Goals

Add a second, small composition root rather than a new application framework. Headless offers every assistant mode, engine and session mode the desktop has, on Windows and on glibc-based Linux x86-64 (not tested). Do not port the window: the hotkey mute, Memory and Performance monitoring, the Install and Sign in buttons and voice preview stay desktop-only.

## Decisions

1. **Load native libraries by explicit path.** A crate-private `native_library` loader returns `libloading::Library`. It uses an absolute path and `LOAD_WITH_ALTERED_SEARCH_PATH` on Windows, `Library::new` with the absolute path on Linux (not tested). Vosk, Whisper and Sherpa (with Piper) go through it, keeping each caller's error context, library lifetimes and preload order. Each runtime names its libraries through a per-platform table: on Linux (not tested) `libvosk.so`, `libwhisper.so` with its `libggml*.so` libraries, `libonnxruntime.so` before `libsherpa-onnx-c-api.so`, and `libpiper_phonemize.so`. On Linux a library's dependencies are loaded first by absolute path in dependency order, so the dynamic linker resolves their sonames to the objects already loaded instead of searching. The exact file names, sonames and symlinks come from a probe of each official archive before its hash is pinned. WinRT stays target-gated.

2. **Use the existing asset store.** The Windows archives stay unchanged. On glibc Linux x86-64 (not tested) the catalogs add, each pinned by SHA-256 and installed through the existing `root` and `keep` fields:
   - Vosk: the [official 0.3.45 wheel](https://pypi.org/project/vosk/0.3.45/#files) (7 173 758 bytes), keeping `vosk/libvosk.so`;
   - Whisper: `whisper-bin-ubuntu-x64.tar.gz` (10 364 195 bytes) from whisper.cpp release `b5454`, CPU only, since the release has no Linux CUDA build;
   - voices: `sherpa-onnx-v2.0.1-linux-x64-shared-lib.tar.bz2` and `piper-phonemize-v1.5.9-linux-x64-shared-lib.tar.bz2`.

   The probe of 2026-11-22 (archives downloaded into `target\linux-probe\`, ELF headers read without extracting) found, with every hash equal to GitHub's published digest:
   - `whisper-bin-ubuntu-x64.tar.gz`: SHA-256 `a72becf15d7917f990f6313867a52638b82b7f9ef237fb0c980dac56a135781c`, 10 364 195 bytes, top folder `whisper-bin-ubuntu-x64/`; real files `libwhisper.so.1.9.5` (soname `libwhisper.so.1`), `libggml.so.0.26.0` (`libggml.so.0`), `libggml-base.so.0.26.0` (`libggml-base.so.0`) and 15 `libggml-cpu-*.so` variants, plus version symlinks and `libparakeet` (not needed). Every library has RUNPATH `$ORIGIN`. They need glibc 2.34 or newer, `libgomp.so.1` (OpenMP, `libgomp1`) and libstdc++ with `GLIBCXX_3.4.29` (GCC 11 or newer).
   - `sherpa-onnx-v2.0.1-linux-x64-shared-lib.tar.bz2`: SHA-256 `532c45bbd41036d83cd70606797529aa8086c2053395a58967736c727625b120`, 9 710 131 bytes, folder `sherpa-onnx-v2.0.1-linux-x64-shared-lib/lib/` with `libsherpa-onnx-c-api.so` (needs `libonnxruntime.so`) and `libonnxruntime.so`; glibc 2.17.
   - `piper-phonemize-v1.5.9-linux-x64-shared-lib.tar.bz2`: SHA-256 `609569420d356f561e13ee6d52ed0edf7dcae225ea498f4cc68587c11d6d295c`, 305 777 bytes, folder `lib/` with `libpiper_phonemize_core.so` and `libpiper_phonemize_cxx_api.so`; glibc 2.14. As on Windows, espeak-ng data comes with each voice.

   The app keeps only the real files, never the symlinks, and loads each library's dependencies first by full path (`libggml-base`, `libggml`, then `libwhisper`; `libonnxruntime` before `libsherpa-onnx-c-api`; `libpiper_phonemize_core` before its C++ API), so the dynamic linker matches each needed soname to the object already loaded. Models (Vosk, Whisper, VAD, voices) are the same files on both platforms. Windows resolves system `curl.exe` and `tar.exe` as before; Linux resolves `curl` and `bsdtar` from `PATH` (`bsdtar` also reads the ZIP-format wheel). No Python runtime or custom unpacker.

3. **One terminal command installs the assets.** `voicebro-server --install-assets` (it replaces the earlier `--install-wake-assets`) resolves what the current settings need through the same requirement functions the join uses: the Vosk runtime and catalog model in realtime voice with the wake word; the Whisper runtime for the chosen device, the model and the VAD model in the Whisper and text answers modes; the voice engine, the voice and, for Piper and Kokoro, the phonemizer in the Whisper mode. Running the command is the operator's approval. It prints each file, its source and size, the phonemizer's GPL-3.0 license when it is installed, and progress; it does not start Discord or an engine and does not change settings or local models. Normal startup lists what is missing and downloads nothing.

4. **Use a standalone `apps/server` binary.** `voicebro-server` is a workspace member built by package name, leaving the desktop and dev probes alone. It uses `paths::data_dir()` and `SettingsStore` and starts through `Runtime::start_checked`, which validates the settings before anything is applied or Discord connects and never rewrites a rejected file. The engines and `EngineSwitch` are built by a core helper that both shells call, so the desktop and headless cannot drift; the desktop keeps the per-engine handles it needs for its own commands. Validation is `Settings::validate` on both platforms; Linux (not tested) additionally rejects a Windows voice (`windows:` ids) in the Whisper mode, where the voice is used. Messages that send people to window controls get terminal variants through `EventBus::for_terminal` without changing the join rules: missing or signed-out Codex, Claude Code and OpenCode, missing wake, Whisper and voice files, and the owner-link log line.

5. **Keep authentication at the existing boundaries.** The Discord token comes from `DISCORD_TOKEN_FILE` when it is set (read into the existing `MemoryStore`, never written), otherwise from the stored token: Windows Credential Manager through `platform_store()`, or on Linux (not tested) `discord-token.bin` in the data directory through the `protect` layer of decision 8. `voicebro-server --set-token` reads one line from standard input, with echo off when it is a terminal, trims it, refuses a blank value, stores it in that place and exits without starting the bot; it never takes the token as an argument. Pass neither token contents nor a token argument to subprocesses. Each engine is found as configured first; on Windows the existing lookups stay, and on Linux (not tested) only `codex`, `claude` and `opencode` on `PATH`, with no Windows fallback. Each engine signs in through its own CLI in a terminal, as the same user and with the same credential location (`CODEX_HOME`, Claude Code's and OpenCode's own folders); VoiceBro stores no engine credential. The Claude subscription notice, a window card on the desktop, is printed once at headless start under the same conditions and enforces nothing.

6. **Stop child processes as a group on Linux (not tested).** On Linux every engine process (the Codex app-server, Claude Code per guild, OpenCode's server) starts in its own process group. Stopping it sends SIGTERM to the group and SIGKILL after a short timeout. A terminal Ctrl+C then reaches only `voicebro-server`, and an npm or launcher script cannot leave its native child running. Windows keeps `CREATE_NO_WINDOW` and the existing lookups, which already prefer native executables.

7. **Share the log filters and the build stamp.** The desktop's log filters (this app's targets at Info, third-party errors, songbird's receive task at Error, detail lines only in a debug build or with `diagnostics.verbose_log`) move into the core and both shells use them. Headless writes `logs/voicebro.log` in the data directory, rotating at 1 MB with one old file kept, and the same lines to stderr. Because `EventBus::log` already writes through the `log` crate, the terminal reporter stops printing log events itself and keeps only the Discord-error exit and the missing-asset summary. `apps/server` gets a build script that computes the same build stamp as the desktop (version, short git hash with a dirty marker, UTC date); it is the first line of every start and the runtime's build stamp.

8. **Every access mode, with the owner link from the terminal.** Headless supports `everyone`, `agreed` and `owner` on both platforms through the existing `OwnerState`, `ConsentState` and `AccessState`.
   - *Link.* `voicebro-server --link-owner` starts the bot as usual, then reads the selected engine's signed-in account as Check does (OpenCode has none) and calls the same `Runtime::start_link` as Link in the window. The code goes to the terminal's standard output only, never through the `log` crate, so it is in neither `logs/` nor the stderr log lines; the docs warn that a service manager may record standard output, so the command is meant for an interactive terminal. Without a signed-in account no code is issued, the terminal says to sign in first, and the bot keeps running. The terminal reports how the code ended (used, expired, five wrong tries) and who was linked; stopping the process ends a waiting code. Linking again replaces the owner, as on the desktop.
   - *Status.* At start the terminal prints the access mode, the linked owner's name or "not linked", and the number of people with a consent record. Owner and consent changes (a link, a removal because the account changed, `/optin`, `/optout`) are printed as they happen.
   - *Storage.* Windows keeps `owner-link.bin` and `consents.bin` DPAPI-encrypted, shared with the desktop under the same Windows user. On Linux (not tested) they are encrypted too: the `protect` layer's `protect` and `unprotect` get a Linux implementation in place of the current "unsupported" one, so the stores, file names and the temporary-file-and-rename writes stay the same.
     - *Cipher.* XChaCha20-Poly1305 with a random 24-byte nonce per write; the file's existing entropy constant is the associated data. A sealed file is a version tag, the nonce and the ciphertext with its tag. Authentication makes any edited byte fail, as DPAPI does.
     - *Key.* 32 random bytes from the OS, created on the first write as `${XDG_CONFIG_HOME:-~/.config}/voicebro/protect.key` with the folder at mode 0700 and the file at mode 0600, created exclusively so two processes cannot write different keys. The encryption key is HKDF-SHA256 of that key with the machine's `/etc/machine-id` as the salt. The key stays outside the data folder, like DPAPI's master key in the Windows profile: a data folder copied to another user has no key, and a key copied to another machine derives another encryption key.
     - *Refusals.* A key file that other users can read, or a missing `/etc/machine-id`, refuses encryption with a message naming the file; nothing is written unencrypted. A missing key, another machine or an edited file makes a file count as no link or no records, reported once at start, as on Windows; a Windows file copied to Linux is such a file.
     - *Crates.* `chacha20poly1305` 0.10 and `hkdf` 0.12 (with `sha2` 0.10), already in `Cargo.lock` through the WebRTC stack, become dependencies of the core on every target, so that the Windows build compiles and checks the format code Linux uses (only Linux calls it); the lock gains no crate.
     - *Optional on Linux.* The new setting `linux.encrypt_files` (default `true`; a file without it reads as `true`) decides how Linux writes the token, the owner link and the consent records. With `false` they are written as plain bytes, still through the temporary file and the rename, with mode 0600, and the terminal warns at every start that they are not encrypted. Every Linux file starts with a format tag (encrypted or plain), so a file is read in either form; at start a readable file whose form differs from the setting is rewritten once in the setting's form, and an encrypted file that cannot be decrypted is left as it is and counts as missing. Windows ignores the setting and always uses DPAPI and Credential Manager. The window does not show the setting: the desktop runs only on Windows.
   - *Terminal equivalents.* Commands that construct no runtime and connect to nothing, meant to run while the bot is stopped (a running bot keeps what it loaded at start): `--unlink-owner` loads the link through `OwnerState` and removes it as Unlink does (an unreadable link file is deleted too); `--list-consents` prints each record's Discord user id, name and time; `--remove-consent <Discord user id>` removes that record through `ConsentState::withdraw` as Remove does, sending nothing to the person; `--clear-token` deletes the stored token (on Windows the Credential Manager entry the desktop app shares). The consent store is opened with the current settings' engine, as at a start. The log lines name the terminal command instead of the window. Cancel stays window-only: a waiting code ends with the process.

9. **Keep cleanup shared.** Tokio signal listeners handle Ctrl+C, Linux SIGTERM (not tested) and Windows console close notification. The main thread leaves the async wait, then calls `Runtime::shutdown()` outside the Tokio async context while the executor is still alive; it waits for Discord and stops every engine and its child processes. Errors after start go through the same cleanup.

## Risks / Trade-offs

- Linux is not tested → every Linux path may fail to compile or run until the user's check; the docs say so, and the Linux tasks stay open for the user.
- Whisper on Linux is CPU-only → document it; pick a small model on a server CPU. A Linux GPU build would need building whisper.cpp from source, outside this change.
- The official Ubuntu build of whisper.cpp may need a newer glibc than older distributions have → document the requirement found by the probe.
- Linux runtime dependencies differ by distro → document the glibc x86-64 scope and the build, asset and C++ runtime prerequisites; do not advertise other targets.
- piper-phonemize is GPL-3.0 → it stays a separate download, installed only when a Piper or Kokoro voice is selected, with its license printed.
- The desktop and headless can point at the same Windows data folder → document running one instance at a time against that folder and bot token.
- Windows can forcibly end a closing console before cleanup finishes → document Ctrl+C as the normal stop mechanism; console close is best effort.
- Headless has no mute control → out of scope; stopping the process or `/leave` ends a session.
- The Linux key file lives outside the data folder → the docs name it next to the data folder; losing it ends the link and the records (link again, people run `/optin` again), as losing the Windows profile does. Root can read it, as an administrator can reach DPAPI keys.
- Linux encryption is our own composition of standard primitives, not an OS service like DPAPI → keep it small, use the vetted RustCrypto crates, and never fall back to writing plain text while `linux.encrypt_files` is on.
- An operator can turn the Linux encryption off → then only file permissions protect the token and the records; the docs, the privacy policy template and a warning at every start say so.
- The link code on standard output may be recorded by a service manager → document `--link-owner` for an interactive terminal; the code is single-use and valid for 10 minutes.

## Migration Plan

No migration is required. The Windows desktop keeps its existing defaults and layout; a settings file without `linux.encrypt_files` reads it as `true`, and the desktop keeps the field when it saves. Use a writable data directory and the same engine sign-ins (same user, same credential folders) on each native run.

## Open Questions

None. The terminal commands for Unlink, Remove and clearing the token were added at the user's request of 2026-11-23 (decision 8).
